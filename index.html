Years of updates, made in a lot of different places

Our platforms grew up separately

Casting Networks and Spotlight have both been improved over the years, just not together. Each change made sense on its own.

The result: lots of variations, no real standard

Add it all up and our design library has drifted into many versions of the same things.

Which makes everything slower

Pushing for updates or building something new gets harder than it needs to be.

Which design system should we use for this?

The question that comes up at the start of almost every project. Right now there isn't one clear answer.

A fully redesigned platform with experiences and interactions that feel thoughtful and intentional.

We can't get there by redesigning on top of what we have today. We need a strong foundation first, and that means starting with the really important basics: our design system.

Why we chose shadcn

We already know it

Design and some of our devs used it on CastIt Studios, Clark's project from a few months ago. We're not starting from scratch.

It's clean, modern, and ours to shape

We can customize it all the way down to fit our brand and how we want our products to look and feel.

It plays really well with AI

It's essentially copy-and-paste code that we own, which makes documentation and coding a lot faster.

The tradeoffs, and how we'll handle them

Updates and bug fixes are on us

There's no registry pushing automatic patch releases. We own the code, so we own the fixes too.

How we'll handle it

We only theme shadcn through our tokens and never edit its source, so pulling in upstream updates stays easy. AI-assisted reviews and visual regression checks help us catch problems early.

Default shadcn can look a little samey

It's so popular that lots of apps built with it end up looking alike unless the theming goes deep.

How we'll handle it

Our own tokens for color, type, spacing, radius, shadows, and motion. Heavy theming is the plan from day one, so the result looks like us, not like a template.

Two ways we could roll it out

Either way, the design system comes first. After that, there's a choice to make.

Redesign page by page

Take one page at a time and give it the full treatment.

What's good

  • Each page gets a fully thought-through experience
  • Big, visible wins we can test and measure

What to watch

  • Old and new pages live side by side for longer
  • Bigger chunks of design and dev work at once

Update component by component

Swap in new components across the platform as they're ready.

What's good

  • The whole platform improves evenly
  • Smaller, lower-risk releases that fit around roadmap work

What to watch

  • Layout and flow problems stick around
  • Pages can look a bit mixed for a while

There are real pros and cons to both. This is one we want to decide together.

Rule of thumb

Don't create a new component just because two screens look slightly different. Use a shared component with a meaningful variant instead.

The plan, in four phases

1

Tokens

  • Name tokens by what they do, like color.action.primary, not blue-600
  • Seven categories: color, type, spacing, radius, shadows, breakpoints, motion
  • Code is the source of truth, Figma is our reference
2

Components

  • Theme shadcn primitives through our tokens, never fork them
  • Only add what a design actually calls for
  • Build up from primitives to components to patterns
3

Docs and quality

  • AI drafts tests, variants, and consistency checks
  • People review everything before it ships
  • Storybook docs and visual regression checks
4

Governance

  • A simple, human-led path for anything new
  • Clear owners for new tokens and variants
  • A plan for communicating breaking changes
The path for anything new:ProposeReviewImplementTestDocumentAdoptEvolve
